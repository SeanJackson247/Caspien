# gt_id: ghost-table prototype for "nullable `ref` = 64-bit id, `ref some` = address"

`gt_id_bench.c` (C, `gcc -O2 gt_id_bench.c`; `./a.out [0-3]` sizes 1e3..4e6, `./a.out L <N>` the lazy-id variants) models the table designs with the same
structure as `stdlib/gt/ghost_table.caspien`: open addressing, linear probing, power-of-two capacity, load <= 1/2, backward-shift deletion, no lock.

Designs: **A** today (set of addresses, 8 B); **B** every object gets an id at registration (addr->id and id->addr indexes, 16 B entries);
**C** id in the object header (+8 B/object) + id->addr index; **D** lazy ids, 16 B address entries `{addr, id}`, id assigned at the first `ref x`;
**E** lazy ids, 8 B address set with the low bit = "has an id", plus addr->id and id->addr tables that only hold objects that were ever referenced.

Findings (8 Oct 2026, 2-core VM, noise ~10-30%; Caspien itself NOT ported yet, this is the data-structure cost only):
- Eager ids (B, C) make every allocation 2-5x dearer (register 100-160 ns vs 40, free 130-185 vs 40 at 1M) whether or not a ref is ever taken.
- Lazy ids with a tagged 8 B set (E) cost a program that never takes a nullable ref exactly what A costs; D costs +10-35 ns per register/free (16 B entries).
- Resolve (`match Some` on an id) is one probe: within about 0-40% of today's alive check. `ref x` of an object that already has an id: one more probe. First `ref x`: 100-230 ns (it creates the id).
- Freeing an object that has an id: 3 table updates, 3-5x today's free. Objects that never had one: unchanged (E).
- Id hash: `id & mask` (ids are a counter, so live ids are consecutive) makes lookups fast but churn 5-10x slower (primary clustering under linear probing); grouping 4 ids per cache line is also worse. Use a multiplicative hash.

## The Caspien version (`stdlib/gt_id/`, design E)

Same five `gt_*` functions (same symbols, same first four `GhostTable` fields, so `alloc_shim.c` and the leak check read it unchanged) plus `gt_ref_id(ptr)` and
`gt_ref_resolve(id)`. Test `tests/gt_id_test.caspien` (60000 random register / moved / alive / ref_id / resolve operations against `tests/gt_id_model.py`; valgrind clean,
4 configs). Benchmark: `python3 benchmarks/gt_id/run_proto_bench.py [N] [REPS]` (programs generated by `make_proto_bench.py`). ns/op, CPU time, best of 3-5, this VM, 1,000,000 objects, `aggressive` preset:

| | A (today) | E, no id taken | E, every object has an id |
|---|---|---|---|
| register | 118 | 117 | 111 |
| alive_check | 56 | 64 | 53 |
| unregister (`gt_moved`) | 74 | 75 | 405 |
| `gt_ref_id`, first call (creates the id) | | | 466 |
| `gt_ref_id`, later calls | | | 133 |
| `gt_ref_resolve` | | | 94 |

100,000 objects (`aggressive`): register 103 / 92, alive 24 / 24, unregister 36 / 38 / 166, ref_id 328 then 65, resolve 36. The other presets show the same shape. So a program that
never takes an id pays what it paid before (differences are inside the 10-30% VM noise); unregistering an object that has an id is about 4-5x a plain one (three table updates);
resolving an id costs about the same as one `gt_alive_check`.
The Caspien tables are ~2-3x slower than the C model above in absolute terms (loads and stores go through `memcopy` helpers), identical in A and E.
