# Bitwise operations: status (1 Oct 2026)

Full account of the design and every file touched: root `CLAUDE.md`, top section. Language reference: `README.md`, "Bitwise builtins and integer literals".

## What exists
Six builtins, all on integers, result has the operand type, no `unsafe` needed:

| builtin | meaning | HOB mnemonic | LOB / register form |
|---|---|---|---|
| `bits_and(a, b)` | `a & b` | `BITS_AND` | `BITS_AND size` / `R_BIN BAND` |
| `bits_or(a, b)` | `a \| b` | `BITS_OR` | `BITS_OR size` / `R_BIN BOR` |
| `bits_xor(a, b)` | `a ^ b` | `BITS_XOR` | `BITS_XOR size` / `R_BIN BXOR` |
| `bits_not(a)` | complement truncated to the operand width (`u8` 0 -> 255, `s8` 0 -> -1) | `BITS_NOT` | `BITS_NOT size` / `R_UN BNOT` |
| `bits_left(a, n)` | `a << n` | `SHL` | `SHL size` / `R_BIN SHL` |
| `bits_right(a, n)` | `a >> n`, logical for unsigned, arithmetic for signed | `SHR` (`SAR` for signed after lowering) | `SHR` / `SAR` / `R_BIN SHR`, `R_BIN SAR` |

Rules:
- Two typed operands (and a typed shift count) must have the SAME integer type. A literal operand adapts to the other operand's type like in arithmetic, if it fits ("'bits_xor': literal 300 does not fit in 'u8'"); this holds for all six builtins and for the shift count. A call with only literals is `u64` (`s64` if an operand is negative); typed limit constants (`u8Max`, `s16Min`, ...) give typed narrow operands in constant expressions.
- Shift counts (decided, one rule everywhere): the count is an unsigned number of its own width; a count at or above the operand's width gives 0 for `bits_left` and for unsigned `bits_right`, and the sign fill (0 or -1) for signed `bits_right`; there is no hardware count masking (`bits_left(x_u64, 64)` is 0, not `x`). Identical in the constant folder, the stack form and the register form, on the Linux AT&T path, the windows_gnu AT&T path and the Intel path.
- Integer literals: decimal, `0xFF` / `0XFF`, `0b1010` / `0B1010`, `_` between digits; normalised to decimal at lex time; typed and range-checked like decimal; usable in `match` arms, `const`, enum values (63-bit), array sizes and range bounds. Malformed forms (`0x`, `0b`, `0b2`, `0xG`, `1__0`, `0x_`) are lex errors; a literal above `u64` max is a type error (it used to crash codegen). `0xFFFFFFFFFFFFFFFF` is 18446744073709551615.
- Optimizer: constant folding of all six at every width (signed and unsigned), only where the runtime result is identical; the inliner, struct unpacking and struct member reordering know the new mnemonics.
- Lowering and backend: address lowering for the new mnemonics, register-form fusion of and/or/xor/not/shl/shr/sar including variable counts, `X86Backend` stack and register forms (shift count in `%cl`, `rcx` saved and restored around it, `rdx` untouched).

Still not available: operator forms (`&`, `|`, `^`, `~`, `<<`, `>>`), octal literals. `StrengthReductionPass` still produces its internal `BITS_AND 8` for unsigned `x % 2^n` and that path is unchanged.

## What was verified (Linux, x86-64, executed)
- `tests/bits_ops_test.caspien` plus `tests/bits_ops_matrix{8,16,32,64}_test.caspien`, generated by `tests/bits_ops_gen.py` with expected values from an independent Python model: 5779 checks, 0 failures, byte-identical output under the four sweep configs (everything on, shipped Linux config, register-form only, everything off). Coverage: every builtin at u8/u16/u32/u64/s8/s16/s32/s64, signed vs unsigned right shift, edge values, shift counts 0 / width-1 / width / width+1 / 63 / 64 / 65 / 127 / 200 / 255 (and negative counts for signed types), constant-folded and runtime forms (function arguments, `atol`, loop variables), stores into struct fields, array and dynarray elements, narrow results passed straight to a vararg, xorshift64, popcount, bit reversal, CRC32 (against `zlib.crc32`), rotates, a SHA-256-style mix, nested calls, literal forms.
- `tests/bits_ops_check.sh`: 34 compile-time cases (wrong arity incl. `bits_not` with two arguments, float / bool / string arguments, mismatched widths and signedness, literals that do not fit, malformed literals, over-u64 literals, forms that must compile), each asserting a non-zero exit and the message text.
- Regression: all 67 programs (the `tests/` programs that existed before this change plus the n-body ports), compiled and run under the four configs with the old tree and with the new tree: identical output in every case. The 14 existing `*_check.sh` scripts and `callee_saved_probe.sh` give the same results as before (`callee_saved_probe.sh` fails with rc 127, "./drv: No such file", in this environment both before and after; not caused by this work).
- Mutation checks of the new code (signed shift fill dropped in the folder, SAR clamp removed, register-form XOR emitted as OR, the SHL/SHR `sbb` mask replaced, `BITS_NOT` result not zero-extended): all caught; the one survivor (`count > w` instead of `>= w` in the folder's SHL) is equivalent.
- windows_gnu: the assembly generated for the bitwise tests (everything on and everything off) assembles with `x86_64-w64-mingw32-gcc -c` and links statically; MASM syntax of the `windows` target was sanity-assembled for a small program with GNU as in Intel-syntax mode (only the pre-existing `movzx rax, dword [..]` loads, which are outside this change, do not assemble there).

## What was NOT verified
- MASM (`ml64`, the `windows` target) was not run at all, and no Windows binary (not even the windows_gnu ones, no Wine here) was executed. The Intel forms of the new instructions are only sanity-assembled as described above.
- No fuzzer; no dedicated LOB-level check script for the new register-form lines (`R_BIN BAND|BOR|BXOR|SHL|SHR|SAR`, `R_UN BNOT`); they are covered through the runtime tests under register-form-only and everything-on.
- Compile time: a program with several thousand folded checks in one function is slow with everything on, because `DeadControlFlowRemovalPass` repeats a whole-function reachability after every folded branch (quadratic); the tests are split into five files for this reason. The pass itself was not changed.
- (Done since, timing re-run included: `stdlib/insecure_hash.caspien` is real 64-bit FNV-1a with `bits_xor`, `stdlib/sha256.caspien` is a real SHA-256, and the Merkle benchmark Caspien programs are real SHA-256; see the root `CLAUDE.md`, top section, and `benchmarks/merkletrees/SPEC.md`.) Found while doing that: the register-form pass only fuses a statement made of plain 8-byte operations on locals and literals; an array element inside a nested expression, or `u32` operands mixed with global arrays, made it fall back to the stack form (about 2x slower for the SHA-256 compression); the Merkle programs keep 32-bit values in `u64` locals for that reason.
